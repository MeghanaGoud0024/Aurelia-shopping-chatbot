# Design Rationale, Assumptions, and What I Would Improve

Required deliverable: the short design rationale, assumptions, and "what I would improve with more time" note.

---

## 1. The decision that shaped everything else

**The language model is a router and a writer. It is never a source of truth.**

Every other choice in this codebase follows from taking that literally rather than treating it as a slogan. The test I applied throughout: *if the system prompt were deleted, would this guarantee still hold?* If the answer was no, the guarantee was moved into code.

Deleting the system prompt today would produce a worse-sounding assistant that still cannot read another customer's order, cancel a shipped parcel, charge without confirmation, or state a price it did not look up.

---

## 2. Decisions with reasoning

### Hand-written agent loop rather than a framework

**Chose:** ~350 lines in `orchestrator.py`. **Over:** LangChain, LlamaIndex, or similar.

A framework would have saved perhaps a day. It would also have put the two things this assignment most needs to demonstrate - exactly where authorisation is injected, and exactly what is recorded for audit - behind a layer of indirection. At seventeen tools and one conversational shape, the abstraction earns nothing and costs the ability to point at a file and say "here is the boundary".

The honest counter-argument: a framework brings streaming, tracing integrations and community-tested retry logic for free. For a production system with a larger team I would revisit this. For a system whose primary claim is auditability, writing it out was correct.

### BM25 rather than a vector database

**Chose:** hand-rolled Okapi BM25 with a retail synonym table and RRF fusion. **Over:** sentence-transformers plus FAISS or Chroma.

Three reasons, in order of weight:

1. The brief forbids special infrastructure. A transformer adds a multi-hundred-megabyte download and a torch dependency without wheels on every Python version.
2. At ~1,100 products, retail search is dominated by exact brand and attribute matching. "Nike" must return Nike, not Adidas because the vectors were close.
3. The parts of semantic search that *do* pay off at this scale can be implemented explicitly: synonyms, suffix normalisation, field weighting, fuzzy brand resolution.

**What this costs:** "something smart for a wedding" has no lexical anchor and retrieves poorly. That is stated in [ACCURACY_AND_LIMITATIONS.md](ACCURACY_AND_LIMITATIONS.md) rather than hidden, and the migration path is one class.

### Synthesised data rather than a Kaggle CSV

**Chose:** deterministic generator. **Over:** a public e-commerce dataset.

A scraped dataset gives real product names and no referential integrity: no orders, no customers, no shipment timelines, no way to test the transactional half of the system. I would have had to synthesise the orders anyway and join them to scraped products, which is worse than synthesising both.

Generating gave referential integrity, byte-identical reproducibility from a seed, and zero PII exposure by construction rather than by policy.

**The cost:** product names are combinatorial rather than real ("Nike Core Unisex T-Shirt"), so the catalogue reads slightly synthetic. Accepted, because correctness of the transactional paths matters more here than catalogue realism.

### Two-phase checkout with a server-issued token

**Chose:** `prepare_checkout` issues a single-use token; `place_order` requires it; the browser redeems it over a separate HTTP route. **Over:** a `confirm: true` boolean argument, or asking the model to wait for confirmation.

A boolean is a value the model can set. An instruction to wait is an instruction that can be argued with. A token generated by `secrets.token_urlsafe` and held server-side is neither.

Binding the token to a fingerprint of the exact basket was added after asking "what if the cart changes between quoting and confirming". The answer was that the customer would be charged for a basket they never saw, so the token is now void if the basket changed.

### Integer cents

Float currency is a correctness bug waiting for a rounding boundary. Cheap to do correctly at the start and expensive to retrofit.

### Stock on the variant, not the product

"Is the Nike tee available in medium?" is a variant question. Collapsing stock onto the product would force the assistant to guess, and it would guess confidently, which is the worst available failure mode.

### Audit tables in the schema from day one

`tool_invocations`, `guardrail_events` and `chat_messages` are in the first commit, not added later. Traceability is a stated requirement, and an audit trail bolted on afterwards is always partial: it records what was convenient to record rather than what was needed.

Writing them on the same session as business data means an audit record and the transaction it describes commit or roll back together. An audit trail that can disagree with the ledger is worse than none.

### Vanilla frontend, no build step

**Chose:** plain HTML, CSS and JavaScript. **Over:** React with Vite.

"Must run from a clean environment using the commands you document" reads badly if the commands include installing Node and running a bundler. The reviewer installs Python dependencies and opens a browser. A design-token system gives the polish a component library would have, without the toolchain.

**The cost:** ~900 lines of DOM code that React would have made shorter. Worth it for a single-page application at this size.

### Errors as data, not exceptions

A raised exception gives the model nothing to act on. A typed `ToolError` with a `recovery_hint` lets it correct the call or explain the limitation in the same turn. Extending this so *ambiguity* is also an error is what produces "which colour would you like?" instead of a silently chosen colour.

### A deterministic planner in the repository

Costs a day. Buys three things: the application is reviewable with no credentials, CI runs with no secrets, and the comparison in [PROMPT_DESIGN.md](PROMPT_DESIGN.md#7-what-the-language-model-is-actually-contributing) is measured rather than asserted.

## 3. Assumptions

**About the deployment**

1. Single process, single worker. Three pieces of state live in process memory; each is documented where it lives.
2. SQLite is adequate. The SQLAlchemy layer is portable, so `AURELIA_DATABASE_URL` can point at PostgreSQL unchanged.
3. The catalogue fits in memory. True at 1,113 products, false at 10 million.
4. One currency, USD, and one locale.

**About the business**

5. Prices are tax-inclusive where displayed; tax is shown separately at checkout.
6. Free standard shipping above $75. Encoded in `cart.py` and in the shipping policy, and these two must be kept consistent by hand - a real system would derive the policy text from the same constants.
7. Cancellation is possible until dispatch; returns for 30 days after delivery, 60 for Gold and Platinum. Encoded in `orders.py` and the policy corpus.
8. Stock is authoritative at read time. No reservation window between add-to-cart and checkout, which is why stock is re-checked inside the write transaction.
9. Order numbers are globally unique integers as strings.

**About the user**

10. One signed-in customer per session, authenticated upstream.
11. Customers may be adversarial. This is why authorisation is in SQL rather than in the prompt.
12. Customers use a modern browser. The interface uses `color-mix()` and CSS nesting-free modern syntax without polyfills.

**About the model**

13. It supports OpenAI-style tool calling and returns valid JSON arguments most of the time. Argument parsing is defensive because "most of the time" is the accurate expectation.
14. It follows behavioural instructions most of the time. This is why the grounding check exists.
15. It is *not* trusted for arithmetic, dates, authorisation, or state transitions.

## 4. What I would improve with more time

Ordered by value, not by effort.

### First week

**1. Span-level attribution.** Link every factual span in a reply to the tool result field it came from, verify each before display, and repair or strike what cannot be verified. This closes the largest remaining accuracy gap and turns the trace from *which calls ran* into *which call produced this exact phrase*. Highest-value item available.

**2. A regression evaluation set.** ~150 question-and-expected-tool-call pairs run in CI. A ten-query version exists for policy retrieval and already earned its keep: it caused a plausible-sounding synonym improvement to be measured, found neutral, and reverted. Tool selection and grounding need the same treatment. Without it, every prompt edit is a small uncontrolled experiment, and that does not scale past one engineer.

**3. Streaming responses.** Server-sent events with tool-call steps streamed into the trace as they happen. Turns a 3-second wait into 300ms to first token, and makes the grounding story *visible* while it happens.

### First month

**4. Hybrid dense retrieval.** Embeddings as a second recall path fused through the existing RRF. The lexical path keeps its precision on brands; the dense path catches intent-shaped queries.

**5. Shared state in Redis.** Quote store, rate limiter and conversation history behind their current interfaces. Prerequisite for more than one worker.

**6. Real authentication and an operator role.** OIDC on `resolve_identity`; `/api/ops/*` behind a role.

**7. Human review queue.** Route every `not_helpful` rating and every ungrounded-claim block into a queue where an operator sees the reply beside its tool trace and can label the root cause. That labelled data is what makes prompt iteration empirical.

### First quarter

**8. Personalisation from order history.** The data is there: size, brand affinity, price band. "You usually take a medium in Nike" is a genuinely better shopping experience, and it needs care - a preference inferred wrongly is worse than none.

**9. Multi-currency and locale.** `Money` already carries a currency code; the formatting and the tax rules are the work.

**10. Semantic caching.** Catalogue questions repeat heavily. Caching on normalised intent plus filters would cut both cost and latency substantially, with careful invalidation on price and stock changes.

## 5. What I would push back on

Two things in the brief I would question before building further.

**"Place purchases through a chat interface"** is the right feature and the wrong default. Conversational purchase is excellent for reorders and for a known item, and worse than a normal product page for anything a customer wants to compare visually. I would ship the assistant as an accelerator beside the catalogue rather than as a replacement for it, and measure whether conversational checkout actually converts before investing further in that path.

**Free-tier rate limits shaped the architecture.** Tool routing and prompt trimming are net improvements I would keep regardless, but they exist because of an 8,000 token-per-minute ceiling. On a production tier I would re-measure whether routing still earns its complexity, and would set `AURELIA_TOOL_ROUTING_ENABLED=false` if it did not. Optimisations that outlive their constraint are a common source of unexplained complexity, so the switch and this note exist together deliberately.
